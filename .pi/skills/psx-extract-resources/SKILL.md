# Extract resources

Run in the current Pi TUI so reasoning and tools stream. Inputs are under
`extracted/`; generated assets/evidence are under `build/assets/`. The loop
continues by committing either a verified asset identification or a tested
parser capability. The user authorized those narrowly scoped iteration commits.

- Use `psx_resource_*` tools and original-byte/specification evidence. No matching
  C, original compiler, gameplay or emulator is required. Missing mappings,
  table bounds, callee semantics and consumer meaning remain explicit blockers.
- Existing supported-format scanning is deterministic. Use inventory, probes
  and original-word CFG/SSA slices for concrete questions. A filename or magic
  word alone is not a validated asset; a supplied archive schema is a hypothesis.
- When an asset is selected, switch to the documentation role: verify/extract,
  record reproducible instructions in `notes/asset-identification.md`, and finish
  through `psx_resource_iteration` action `asset`. Generated bytes are not committed.
- When existing parsers cannot make progress, the controller invokes
  `psx-build-resource-parser`. Build a capability with evidence and tests, rather
  than repeatedly rescanning unchanged bytes or fabricating a format.
- Stop only on the selected iteration's gated commit, cancellation, explicit
  budget, verification failure or an honestly unsupported builder attempt.
  The controller—not free-form prose—decides whether an iteration succeeded.

Keep discovery, extraction, decoding, interpretation and export distinct. A
round trip proves preservation, not member meaning. Total game asset count is
unknown. No forked agents/worktrees, source/header/build rewrites or automatic
changes outside the selected parser or asset-note scope.
