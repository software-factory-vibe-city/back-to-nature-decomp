# Task 2 — optional declaration integration and partial-view merging

Status: **planned and deferred; optional enrichment** of
[Task 1](01-context-and-handoff.md). The active next work is
[callgraph-driven type propagation](callgraph-type-propagation.md), not declaration
publication. Task 1 must remain usable with this pass absent or disabled. The old
repair implementation is already retired; this is not its replacement under
another name.

## 1. Objective and boundary

Perform the justified declaration work agents currently do by hand after seeing
an m2c draft:

- Find and include an existing type/prototype instead of redeclaring it.
- Reconcile a generated object view with the actual global/backing symbol.
- Publish genuinely new shared/local-parameter types or global overrides in the
  designated hand-maintained headers, then regenerate derived context.
- Reuse, extend or merge compatible partial struct views when evidence shows
  they describe the same storage or record family.
- Preserve translation-unit ownership and the addressing it produces.

This pass consumes declarations and evidence. It does not guess scalar types,
repair control flow, tune instruction scheduling, fix pointer scaling after the
fact, fabricate missing call arguments, or make source compile at any cost.
Those are upstream context/decompiler defects or agent-discovery work.

Its input is Task 1's immutable packet plus the current declaration index. Its
output is a deterministic proposal, evidence, dependency impact and validation
result. It may return a useful partial proposal alongside explicit conflicts.
No-change and needs-discovery are normal outcomes, not pass failures to hide.

## 2. Proposed flow

```text
Task 1 raw draft + structured facts + existing declaration index
    → identify storage/type identities and required declarations
    → reuse / compatible extension / new view / conflict
    → AST-based candidate patch in an isolated workspace
    → regenerate context; compile and compare affected functions
    → accept validated transaction, or retain proposal for discovery
    → refresh Task 1 measurement and handoff / exact-match route
```

Keep the original draft and pre-integration measurement. Record the exact edits
and post-integration measurement separately so the incremental value of this
pass can be backtested. It must be possible to run it in report-only mode, before
handoff, or after an agent has supplied a missing fact. No unbounded cycle of
repeated merging and recompilation.

Only an explicitly authorized automatic preparation invocation may apply the
validated transaction. Inspection/proposal modes remain read-only. Task 1's
freshness, scope, resume, cancellation and finalization rules still apply.

## 3. Typed input, not printed-name heuristics

Prefer structured facts from m2c and the static context analysis:

- Declaration/type origin and scope; whether complete, partial or inferred.
- Storage identity, container/lifetime, base expression and base bias.
- Field intervals, widths, signedness, pointer/pointee constraints and alignment.
- Observed strides, array indexing, address-taking and extent constraints.
- Locations of uses in the draft and other known sources.
- Witnesses and assumptions for each fact.

An `unkC` spelling is not, by itself, proof that a field starts at offset `0xC`.
A generated byte array may be padding, a real accessed array, or an uncertain
region. Preserve that distinction explicitly. Add structured m2c metadata if
necessary; do not replace a lost fact with a regular expression over its output.

Use the repository's pinned AST parser for declarations and source edits.
Malformed `?` declarations and broken syntax must be represented as unresolved
input or consumed through structured decompiler facts, not “repaired” by unsafe
range substitutions. Edits to a declaration are unique and non-overlapping even
when many call sites use it.

## 4. Resolve storage and declaration destinations

Model linker/storage identity separately from the C spelling exposing it.
Consult the existing global override and alias patterns and their actual
preprocessed semantics. A macro can expose a scalar, pointer, array or biased
subobject view over a differently named backing declaration.

For each needed declaration, choose one explicit action:

1. **Reuse:** an existing declaration and its scope already satisfy all uses.
2. **Expose:** include the owning header or publish a known type to its proper
   shared location, without changing its meaning.
3. **Extend/merge:** incorporate compatible evidence into an existing partial
   view under the rules below.
4. **Create a view:** establish a new evidenced partial or complete type where
   no compatible existing view exists.
5. **Conflict/unknown:** retain the draft and identify the discovery needed.

Use the header roles from `configs/project-profile.md`: shared parameter/local
types belong in `include/game_types.h`; global type overrides belong in
`include/globals_override.h`. Regenerate `include/globals.h`, function context
headers and m2c context through their generators. Do not hand-edit them.

Do not redeclare a generated global in a function source. Preserve or add a
required tentative definition only with translation-unit ownership evidence;
never enlarge an array to force absolute addressing. Existing assembler-symbol
alias declaration idioms must be understood and checked against source policy,
not copied as a route to introduce new assembly workarounds.

SDK objects reuse SDK definitions and operation boundaries; this pass does not
invent a competing struct for a known SDK type. Function declaration handling
uses Task 1's witnessed contracts and graph-propagated constraints, retaining
provenance, full types and ABI slots rather than shortening prototypes to suit
one caller. Partial constraints are not complete publishable signatures, and
callback-table members do not acquire a uniform prototype by being co-located.

## 5. Conservative partial-struct merging

This capability is in scope. It must solve the actual repeated work of combining
compatible known pieces, while distinguishing compatibility from identity.

### 5.1 Establish identity before combining constraints

Require positive evidence that the views describe the same object or record
family: the same resolved storage, a traced allocation/base, an independently
supported array element relationship, or a known typed interface with proven
pointer flow. A generic helper receiving both addresses is not enough.

Normalize every field offset against that identity, including base-biased aliases
and interior pointers. Include container/load lifetime: identical numeric RAM
addresses in different overlays do not establish object identity. Neither
matching field names nor similar layouts establish it either.

### 5.2 Unify compatible constraints

For an established identity:

1. Normalize access intervals and layout constraints using the target ABI.
2. Deduplicate equivalent facts while keeping every witness.
3. Combine non-overlapping fields if their offsets/alignment are compatible.
4. Reconcile compatible existing typed fields without discarding qualifications
   or pointee information.
5. Split **known generated padding** to expose newly witnessed fields. Never
   silently reinterpret a real accessed byte array as padding.
6. Verify independently observed element strides and complete-size constraints.
7. Emit a deterministic canonical view and a mapping from old view/field names.

Partiality remains explicit. A final observed access at offset N does not prove
the record ends there. Keep a minimum accessed extent separate from a proven
complete size. C structs have concrete sizes; do not use a partial struct as an
array element, by-value object, or pointer-step unit unless its required size
and alignment are established. An uncertain terminal extent is a discovery item,
not permission to select the smallest compiling layout.

### 5.3 Conflicts are useful outputs

Return both interpretations and the relevant uses for:

- Overlapping fields with incompatible widths or semantic types.
- Signed/unsigned reads whose shared source type is not established.
- Pointer versus scalar or incompatible pointee interpretations.
- Conflicting base bias, stride, alignment or complete-size observations.
- Possible union/overlay views, temporal reuse, or unrelated local type names.

Separate views may be legitimate. Do not automatically manufacture unions,
packed structures, casts or blanket byte arrays to suppress the conflict.
Layout compatibility alone is not authorization to merge two records.

### 5.4 Concrete regression case

The current `Ovl11RangeEntry` view of `D_80124A18` in
`include/globals_override.h` combines accesses from `ovl_11_func_800EFD54` and
`ovl_11_func_800EFABC`: a halfword at `0x08`, words at `0x0C` and `0x10`, and a
`0x14` record stride. Use the original accesses and historical partial views as
a positive merge fixture; the final handwritten declaration is an expected
outcome, not knowledge secretly supplied to the candidate.

Pair it with negative fixtures that have the same offsets but different storage,
the same RAM address in different overlay lifetimes, a biased pointer with an
inconsistent base, and a real byte array overlapping a proposed field. This
prevents a “union all matching offsets” implementation from passing the test.

## 6. Transactional publication and dependent validation

Changes to a shared type can affect code far from the target: `sizeof`, pointer
increments, indexed addressing, field offsets, stack layout and by-value ABI.
Checking only the current function is insufficient.

For each proposal:

1. Capture source/header/generator fingerprints and the baseline match status
   of dependents. Compute the affected source/type/include closure across all
   configured containers; fall back to broader validation if closure is uncertain.
2. Generate a minimal patch in isolation, with origin-to-destination mappings.
   Preserve comments and unrelated declarations; rename uses through AST identity,
   not global text replacement.
3. Check offsets, sizes and alignment with the configured target compiler using
   C89-compatible layout assertions/probes. Host layout is not an oracle.
4. Regenerate derived headers/context and compile affected translation units.
5. Re-run the per-function byte oracle for every previously matched affected
   function; preserve all of those matches. Measure the target's staged residual
   and report any traded result rather than selecting edits by a byte score.
6. Run scope/source-policy and full configured binary checks before promotion
   when the staged target is finalizable. For an unfinished target, establish
   collateral safety against the buildable baseline separately and keep its
   nonmatching candidate status explicit; never report a full finalization pass.
7. Recheck live fingerprints and apply the validated, dependency-complete
   transaction, or return stale/conflict without overwriting newer work.
8. Refresh the prepared packet and context caches from the accepted declarations.
   Only the normal full finalization gate can send an exact target to documentation.

Do not let a check of the original assembly stub stand in for validation of the
new C. Conversely, an unfinished target's expected mismatch must not conceal a
regression in a previously matched dependent. Keep these two verdicts separate.

A failed proposal leaves shared live headers unchanged. If publication is
interrupted, use an owned-file journal/fingerprint check to recover or refuse;
never reset unrelated dirty files. Filesystem-wide atomicity is not assumed.
The second application of an unchanged accepted proposal must be a no-op.

## 7. Delivery slices and tests

### A. Existing declaration reconciliation

Implement reuse/include selection, known alias resolution and correct destination
selection first. Test scalar/array/pointer macros, source-local typedef scope,
SDK reuse and ownership-sensitive definitions. Multiple uses must produce one
edit. Dry-run and no-change output must be stable.

### B. New view publication

Implement evidence-backed new declarations and generated-header regeneration.
Test unresolved types, partial extents, missing ABI slots, declaration cycles,
conflicting names and macro collisions. They must not produce fake definitions.

### C. Partial-view coalescing

Implement storage identity, base normalization, compatible merge and explicit
conflict results. Test generated-padding refinement, proven stride, insufficient
extent, overlapping accesses, qualifier differences and overlay lifetime isolation.

### D. Transaction and harness integration

Test dependent-match preservation, rejected layout changes, stale inputs,
interrupted publication, dirty user files, idempotence and report-only operation.
Use the same preparation/handoff schema and full-gate path as Task 1, not a
second competing bundle or a private success criterion.

Run the relevant AST/context/build/controller tests, project TypeScript checks,
the full suite and configured binary checks. Then compare Task 1 alone with
Task 1 plus this pass under the [backtest protocol](03-session-backtesting.md).

## 8. Release criteria

- Task 1 remains functional with the pass absent or disabled.
- Every automatic declaration change has evidence, a destination, a reversible
  patch and a validated dependency closure.
- No false merge, implicit scalar fallback, generated-header hand edit, policy
  violation or collateral loss of an existing match is accepted.
- Historical positive declaration/merge cases are handled and negative cases
  are left explicit for discovery.
- Controlled evaluation shows incremental reduction in declaration work or
  end-to-end cost without reducing solve outcomes. A higher raw compile rate
  bought by incorrect type/ABI assumptions is a regression, not success.
