# func_80014494 — the natural source was right all along; the flag was missing

**Status: matched (48/48 words), clean C, under an allowlisted
`-fno-cse-skip-blocks` per-file flag override.** `make check` is green.

The source is the most obvious C anyone would write for this function. Every
earlier session contorted it — pointer increments, two-pointer forms, cast
address families — because the contortions bought back instructions that the
missing flag had removed. Recognising that is the whole retro.

## What the function is

`D_8005EA18` is two eight-byte `PadSetAct` actuator tables (proven by
`func_80014064`, which hands `&D_8005EA18` to port 0 and `&D_8005EA18 + 8` to
port 0x10). `func_80014494` fills one port's table. First call for that port
(`D_8005E3E8[port] == 0`): write the 0x40 header byte, set `[1]` from
`arg0 != 0`, force it to 1 when `arg1 != 0`, and clear `[2]`. Later calls: set
`[1]` from `arg0 != 0` and `[2]` to `arg1`. Then clear both tables when
`D_8005E3EC == 0`.

## The residual, and why it looked unreachable

Two facts had to hold at once, and under baseline flags they are mutually
exclusive:

1. **The join block of the inner `if` re-forms the symbol address.** At
   `0x800144F4` the target emits `addiu $v0,$t2,%lo(D_8005EA18)` even though
   the dominating block already materialised the same address in `$v0` at
   `0x800144C4`, with no call or clobber between. The same block *does* reuse
   the dominating block's `sll` result in `$a0`, so it is not CSE-starved.
2. **Every pointer pseudo in the then-block is single-set.** `sched.c`'s
   `birthing_insn_p` boosts an insn to `LAUNCH_PRIORITY` only when its
   destination is live *and* `REG_N_SETS == 1`. The old scheduler runs
   bottom-up, so an unboosted insn floats to the top of the block. The GCSE
   copy `move $t2,$v0` sits at the end of the block pre-scheduling and has the
   largest LUID, so it wins every unboosted tie and sinks — unless nothing
   else in the block is unboosted. It lands right after the `lui` in the
   target, which means nothing else was unboosted, which means no pointer was
   assigned twice.

Fact 1 was what every pointer-increment shape was buying: `p++` makes the base
pseudo multi-set, CSE loses it, and the join re-forms the address. But that is
exactly what breaks fact 2. Twenty-one source shapes were swept across the
pointer-increment, two-pointer, row-pointer, offset-local, function-scope,
`char *`, pre-increment and cast address families. They collapse to two
outcomes: 47 instructions with the right schedule, or 48 instructions with the
wrong one. Neither is the target.

## What actually decides it

`cse.c`'s `cse_end_of_basic_block`, under `-fcse-skip-blocks` (on at `-O2`),
follows a conditional branch that jumps *around* a block — "detect a branch
around a block of code" — when the target label has exactly one use. Our inner
`if` is precisely that shape, so CSE carries the base pseudo across the skipped
body into the join and folds the `lo_sum` away. `invalidate_skipped_block`
only invalidates what the skipped block *sets*, and the skipped block sets
nothing relevant. No source shape reaches past this: the condition depends on
the CFG, and the CFG is fixed by the semantics.

With `-fno-cse-skip-blocks`, the join block is its own CSE block, keeps its
`lo_sum`, and GCSE still removes its redundant `high` and `sll` — because GCSE
hashes on register operands, so the two `lo_sum`s (different `high` pseudos)
are different expressions to it while the `sll`s are the same. That is exactly
the target's asymmetry: `sll` reused, `lo_sum` re-formed.

## Evidence for the flag

- **Fingerprint:** the re-formed `lo_sum` at `0x800144F4` beside the reused
  `sll` in the same block. Decoded from the original bytes, no source needed.
  Not one `flagProbe` detects today — `flagProbe`'s fingerprint set only knows
  the unsplit-macro-load lui/lw class, and its flag matrix does not include
  `-fcse-skip-blocks`. Both are worth extending.
- **Dominant column:** natural array-form source goes from 47 instructions /
  13-of-48 to a byte-exact 48/48 the moment the flag is applied. Baseline
  cannot reach it from any of the 21 shapes swept.
- **No contrary regional witness:** all six matched members of the
  `0x80013B04–0x80014554` pad group (`func_80013B04`, `func_80013F90`,
  `func_80014064`, `func_800140C8`, `func_800142D8`, `func_80014554`) were
  re-diffed with `-fno-cse-skip-blocks` applied and every one still reports
  `MATCH`. The flag is consistent with the whole group, not fitted to one file.

## Method note worth keeping

The decisive measurement was `cc1 -fsched-verbose-5 -dS`, which prints the
ready list and `INSN_PRIORITY` at every cycle. Two minutes of that replaced
several rounds of guessing at allocator behaviour, and it is what exposed the
`REG_N_SETS == 1` gate. This project builds with the **old** `gcc/sched.c`
scheduler, not `haifa-sched.c`: it is bottom-up, `T-N` counts down to the last
insn, and `rank_for_schedule` there is a different function from the
identically-named one in `haifa-sched.c`. Reading the wrong one models the
wrong machine.

## Tooling defect fixed in the same change

`source-policy.ts` keyed the `flag-override` allowlist lookup on the patch
scope, which is empty when the caller audits the whole repo instead of one
function. A correctly allowlisted override therefore passed the per-function
gate and failed the repo-wide sweep. The lookup now keys on the stem named in
the `CC1FLAGS_` line itself.
