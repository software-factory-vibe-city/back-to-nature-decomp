## 1. The residual was one leaf's position in the loop preheader

```asm
/* target */                        /* prior best */
move  v1,zero                       move  v1,zero
li    t0,8                          li    t0,8
addiu a0,sp,16                      li    a3,17        <-
lui   v0,%hi(D_8006C838)            addiu a0,sp,16
addiu a2,v0,%lo(D_8006C838)         lui   v0,%hi(D_8006C838)
addiu a1,a2,0x5252                  addiu a2,v0,%lo(D_8006C838)
li    a3,17                <-       addiu a1,a2,0x5252
sw    ra,96(sp) ...                 sw    ra,96(sp) ...
```

The old `sched.c` scheduler walks block 0 backward and takes ready
instructions in descending LUID (program-order) order. A chain such as
`lui`/`addiu` is promoted next to its consumer when it becomes ready. The
sched1 dump shows both behaviours: `ready list at T-1: 336 330 321 319 304 12`,
then `9 (7f000001)` and `8 (7f000001)`.

So the constant 17 lands last only if it is created after the giv
initialisations. The second loop pass is the one that creates it there:
pass 2 emits its movables after pass 1's giv inits. The previous session
derived this requirement correctly.

## 2. Both sides of the desirability test came from the source

`move_movables` moves an invariant only if
`threshold × savings × lifetime >= insn_count`.

- `threshold` starts at 58 in a loop with no call (`loop.c:701`).
- It loses 3 after every movable that moves (`loop.c:1934`, `:2138`).
- `insn_count` is the loop's size at pass 1, *before anything is hoisted*.

| first loop pass, loop 1 | `insn_count` | `threshold` at `== 8` | `threshold` at `== 17` | result |
|---|---|---|---|---|
| all slot reads through the local `base` (prior best) | 34 | 55 | 52 | both move in pass 1, so 17 is too early |
| all slot reads through `D_8006C838` directly | 48 | 46 (< 48) | — | both are deferred, so 8 is too late |
| indexed reads through `base`, fixed reads through the global (committed) | 44 | 52 | 43 (< 44) | only 17 is deferred; pass 2 moves it (29 insns) |

Each direct global access adds a `high`/`lo_sum` address computation inside
the pass-1 loop. That raises `insn_count`. When the computation is hoisted,
it also costs the threshold 3.

None of this is visible in the final loop: the hoisted computations merge
with the preheader's base address. The final loops are identical across all
three rows. Only the pass-1 loops differ.

The sweep tried all 16 global-or-local choices for the four reads in one run
(`build/9be4_claude/v2/`). Exactly two were exact:

- `m10`, the committed shape;
- `m05`, its mirror image: indexed reads through the global, fixed reads
  through the local.

The margin is one instruction: 43 against 44.

**Transfer:** when the target needs a constant hoisted in pass 2, treat
`insn_count` and the threshold decay as source-side variables. In-loop
invariant work that is later hoisted raises the first and lowers the second,
and leaves nothing in the final assembly. Sweep it as a grid over the access
sites that lie, in loop order, between the movables whose decisions must
differ.

Evidence:
- `build/9be4_claude/{base,final}.i.loop` and `build/9be4_claude/v1/slots_glob.i.loop`;
- `build/9be4_claude/base.i.sched`, the block 0 ready lists;
- `tools/vendor/gcc/2.95.2/src/gcc/loop.c:1837`, the desirability clause.

## 3. The closure that ended the search had a false premise

The previous session's `psx_loop_trace` closure reads:

> 17 declines only if threshold<34, i.e. 9 moved movables before it
> (currently 2) or moved_once[regno]

It is recorded as conditional on "current 85-word source and the target's
identical loop body".

The arithmetic is right for that source. The premise is wrong in two ways:

- **34 and 2 are facts about that source, not the target.** They describe
  that source's pass-1 loop.
- **"Identical loop body" holds only after hoisting.** Many pass-1 bodies
  compile to the same final loop.

So the closure fixed the one quantity the source controls and then showed it
could not move. Its "do not re-run" label then sent the remaining work back to
preheader spelling:

- statement order;
- explicit pointer walkers;
- holding 8 and 17 in variables.

That is the place the scheduler analysis had already ruled out.

**Transfer:** before recording an impossibility built from a pass's internal
counts, ask whether a different source could produce those counts and still
reach the same final code. If it could, the closure is conditional on the
source, and the condition belongs in `--conditional-on` in those terms.

Evidence: `build/experimentLedger/closed/ovl_11_func_800F9BE4.jsonl` (rows of
16:03:18 and 16:07:55). They remain as recorded; this match refutes the second.

## 4. The data model was not the lever this time

m2c's draft treated the table as raw arithmetic (`tbl[i * 3 + 3]` on
`D_8006C838 + 0x5252`).

- **The natural reading compiles identically.** That reading is 18 six-byte
  slot records at +0x524C, read as `slots[i + 2]`, `slots[0]`,
  `slots[i + 1]` and `slots[1]`. In `do` or `for` form it produces the same
  words as the draft (`build/9be4_claude/v1/`).
- **The type only made the sweep possible.** With the slot view, each read
  is one site that can be spelled two ways.
- **The lever was the route each read takes to the base**, not the type.

**Transfer:** a declaration change that leaves the output identical is still
worth keeping when it turns the residual's lever into a finite set of
per-site choices.

## 5. What the tools showed and what they missed

- **`psx_target_loop_emission` stated no goal.** On the prior best it said
  "No preheader group is constrained past its own evidence" and read block 0
  as "nothing hoisted".
  - The prologue saves (`sw ra/s1/s0`) that sched2 places at the end of the
    block are classed `effectful → source`. The non-decreasing class sequence
    then pins every earlier group to `source`.
  - The candidate side reported "no loop in the trace could be joined to it".
  - So the triage `loop-preheader-order` signal carried the layout but no
    `REQUIRED of the original` line. The requirement had to be derived by
    hand through `psx_analyze_target_schedule`.
- **`psx_loop_trace` printed the comparison but no way to flip it.** It
  showed "insn 95: threshold 52 … needs product >= 1, has 1 -> moves", which
  is correct. Nothing said how far the source was from flipping that
  decision, or which source changes move the two sides.
- **The triage `loop-nesting` detector fired falsely.** It listed loop 1's
  instructions as "invariant in inner loop" for loop 2's inner loop, but the
  two outer loops are sequential, not nested. That noise competed with the
  right signal.
- **Older ledger sources can't be replayed as-is.** They reference
  `Ovl11F9BE4View`, which was replaced in `include/game_types.h`. A
  self-contained copy of the prior best, with that typedef inlined, is
  `build/9be4_claude/prior_best.c`.
