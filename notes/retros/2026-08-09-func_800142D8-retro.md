## What the function is

Distance-from-centre with a dead zone. Mask both coordinates to eight bits;
return 0 when both are inside `[0x5C, 0xA4]`; otherwise `csqrt` of the squared
distance from `(0x80, 0x80)` in 12-bit fixed point, truncated toward zero,
minus `0x25`, clamped to `[0, 0x5A]`.

## Where the session started

The inherited source scored 38/45 with **three broken webs**: the sum landed in
`$v0` instead of `$a2`, the shifted call argument followed it, and the initial
mask schedule was inverted. The inherited header comment attributed this to an
allocator preference problem and listed fifteen families of source shapes tried
against it.

That framing was wrong in a specific way worth recording: it treated the
`$a2` sum as an *allocation* question. It is a *scheduling* question, and the
scheduler decision is downstream of a property of the source that has nothing
to do with the arithmetic — how many times an unrelated variable is assigned.

## The two mechanisms that moved it

### 1. `sched.c` birthing boost — assign the mask variable exactly once

The target orders block 0 as `[mask Y, copy, mask X]`. Every attempt produced
`[mask X, mask Y, copy]`, which kills the whole downstream structure: `arg0` is
dead by the time the copy is born, so the copy web does not conflict with `$a0`,
and global allocation hands it `$a0` instead of `$a2`.

All of block 0's insns have computed priority 1, so ordering is decided entirely
by `adjust_priority`: a newly-ready insn is raised to `LAUNCH_PRIORITY` only
when `birthing_insn_p` holds, and that requires `REG_N_SETS == 1` for the
destination pseudo. The inherited source reused `x` for the post-`csqrt` clamp
value, so the X-mask insn was never boosted and lost the tie to the copy.

Giving the clamp its own variable made `x` single-set, which boosted the X mask,
which pushed the copy one cycle earlier, which kept `arg0` live across the
copy's birth, which forced the conflict with `$a0`, which produced `$a2`.
One variable split; three separate defects resolved at once.

The birthing boost is already documented in
`notes/research/func_80019070-prologue-allocation-and-arg2-truncation.md` and
`notes/research/func_800154CC-polyf4-diamond-crossjump.md`. It was re-derived
from the vendored `sched.c` here because the diff was classified as an
allocation problem and the notes were searched by symptom words that did not
include "wrong order of two independent initializers". That is the lookup
failure to fix, not the mechanism.

### 2. `cse.c` cheapest-register swap — do not let a copy follow its source

The target's `move $a2,$a1` is a real register copy in the source. It survives
only when the copy statement is **not** immediately preceded by the insn that
defines its source.

`cse_insn` ends with a rule for `(set REG0 REG1)`: when the immediately
preceding insn sets `REG1` and `REG0` has become the quantity's canonical
register, it rewrites the previous insn to set `REG0` and turns this insn into
`(set REG1 REG0)`. Later uses then canonicalize onto the new register and the
copy becomes dead. `REG0` becomes canonical (`make_regs_eqv`) when its last
mention is later than `REG1`'s — which is exactly the case for a copy that is
reused for the arithmetic.

So `y = arg1 & 0xFF; t = y;` loses the copy, and
`y = arg1 & 0xFF; x = arg0 & 0xFF; t = y;` keeps it. The intervening statement
is load-bearing, and it is the natural way to write it anyway.

## The residual

```
target:     beqz $v0,.L314 / slti  $v0,$a2,0x5C      fall-through thread
candidate:  beqz $v0,.L318 / addiu $v0,$v1,-0x80     target thread
```

`fill_eager_delay_slots` picks a thread per branch. Taking the fall-through
insn MOVES it and the count stays at 44. Taking the target insn COPIES the
calculation block's first instruction and redirects the branch past it, which
is the extra instruction. The target does the second thing for guard branch 3
(`bnez`, predicted taken) and the first for guard branch 2 (`beqz`, predicted
not taken); the candidate does the second for both.

Standalone probes confirm both behaviours are reachable with this compiler:
a three-branch guard over a short calculation block reproduces the target's
exact pattern — `beq` branches take their fall-through insn, the `bne` steals
from the target and redirects. The same guard over this function's calculation
block does not.

## Premises eliminated, with evidence

The four things that could be wrong other than the source shape. All checked.

- **Signature.** Arity 2, 3 and 4 (unused extra parameters) produce
  byte-identical output. Not the arity.
- **Flags.** `flagProbe` detects no target fingerprint. Seven columns; the only
  one reaching 44 instructions, `-fno-rerun-cse-after-loop`, scores 34/44
  because dropping cse2 deletes the `move $a2,$a1` copy. Probe reverted,
  nothing adopted.
- **Assembler.** The vendored `maspsx-delay-slot-fill.patch` claims real ASPSX
  fills a delay slot from the *following* instruction, which is exactly the
  defect's shape. Tested directly: `psyq_sdk/psyq/bin/ASPSX.EXE` 2.86 under
  wine, on a control (current cc1 output) and on a hand-edited input with
  branch 2 left unfilled under `.set reorder`. Real ASPSX emits `nop`; it does
  **not** forward-fill. The control reproduces the maspsx+gas output exactly.
  The target's delay-slot fill is cc1's `dbr`, not the assembler. Caveat: the
  vendored binary is 2.86, the project targets 2.80 — same 32-bit wine-era
  family, not the identical build.
- **The pinned tail.** 576-variant search over rounding form, mask split, both
  clamp spellings, return form and declaration order. Every axis inert; results
  split 288/288 on one bit (post-call web membership), and the 44-instruction
  half is contradicted by the target's own registers (`$a2` is dead after
  `sll $a0,$a2,12`, so the `csqrt` result cannot be on the `t` web).

Also excluded: `analyzeTargetSchedule` and `searchSchedulerState` replay
`.sched` and `.sched2` **exactly**, all 12 blocks, both stages. Not a scheduler
problem, and no scheduler-state search will reach it.

## The decisive result: exhaustive web-partition sweep

Scripts and logs: `build/bruteForce/func_800142D8/`.

Enumerated **all 1,057,675 legal variable assignments** over this statement
skeleton — two value roles may share a variable only where their live ranges are
disjoint. Filter: cc1's instruction stream must equal the target's
42-instruction stream (`expected.txt`; the current file's 43 minus the duplicate
at index 10, label names wildcarded). Runtime about five minutes on 22 cores.

**Zero exact matches.** The statement skeleton is wrong, not the naming.

Prefix-scored rerun (`bf2.py`): **13,368 partitions reach prefix 12, none 13.**
Prefix 12 covers instructions 0–11, which includes `slt $2,$6,92` sitting in
branch 2's delay slot — the defect, solved. One was byte-verified: exact through
`0x80014304`, first differing word `0x80014308`. The current file reaches
prefix 10.

So guard-correct is reachable 13,368 ways; guard-correct **and** calc-correct is
not, under any renaming. That is proven over the complete space, not argued. No
pairwise role-merge is common to all 13,368 — they range from 4 to 10 distinct
variables — so it is not one trick.

Scope caveat: the filter compares cc1 *text*, so a variant emitting
`addu $6,$5,$0` where cc1 normally emits `move $6,$5` would be rejected despite
identical bytes. Same pattern for the same RTL, so the risk is low, but the zero
result is scoped to that filter.

## Resolution: the granted exception, and what it cost

The user granted the embedded-asm exception once the clean-C space was proven
empty. The intent was explicitly "as little as possible, but make it match".

The final shape is three instructions of 44 — guard branch 2 and nothing else:

```c
if ((u32)(x - 0x5C) < 0x49) {
    /* if (t >= 0xA5) goto calc; cond = (t < 0x5C); */
    __asm__ __volatile__(".set\tnoreorder\n"
                         ".set\tnomacro\n"
                         "\tslt\t%0,%1,165\n"
                         "\tbeq\t%0,$0,$L3\n"
                         "\tslt\t%0,%1,92\n"
                         ".set\tmacro\n"
                         ".set\treorder"
                         : "=&r"(cond) : "r"(t));
    if (cond == 0) {
        return 0;
    }
}
```

Everything else stayed C, and that is what keeps the block this small:

- **No hard-register pinning.** The operands are plain `"=&r"` / `"r"`, so cc1
  still does the allocation, and it independently picks `$v0` for `cond` and
  `$a2` for `t` — the target's registers. The early-clobber matters: without
  `&`, cc1 may tie the output to the input and emit `slt $a2,$a2,165`.
- **Branches 1 and 3 stay compiler-generated.** Branch 1 is the enclosing
  `if`; branch 3 is `if (cond == 0) return 0;`. `dbr` then does the two things
  it was already doing right on its own — fills branch 1 from the preceding
  block (`move $a2,$a1`) and steals `addiu $v0,$v1,-0x80` from the target of
  branch 3, redirecting it. Only the middle branch had to be written out.
- **The `csqrt` call stays C**, which is the only reason the frame is right.
  `subu $sp,$sp,24` is `16` bytes of outgoing-argument space plus the `$ra`
  slot; `current_function_outgoing_args_size` is zero without a real call, so
  a whole-function asm block would have produced an 8-byte frame. That, plus
  the fact that inline asm cannot branch to a compiler label, is what bounds
  how much of this function could be written by hand at all.

`$L3` is cc1's own label for the join after the `if` — the calculation-block
entry, and the target of all three guard branches before `dbr` rewrites them.
Referencing a compiler-internal label from asm is the ugly part of this fix. It
is stable for this source and compiler, and it fails loudly (`as`: undefined
symbol) rather than silently if it ever moves.

### The trap that cost a build

Written with spaces (`.set noreorder`), the directives do not match maspsx's
exact-spelling state tracking, so maspsx passes them through to `gas` instead of
consuming them. `gas` then re-enables reordering **for the rest of the
function**, refills every later delay slot, and emits 50 instructions for
36/50 words — with no diagnostic from any stage. The tabs are load-bearing.
Recorded in the source file too, because a formatter would break it.

### Four gate defects this change surfaced

Being the first function to exercise the embedded-asm path end to end turned up
four bugs in the machinery that is supposed to police it. All are fixed here,
each with a regression test:

- **`source-policy.ts` did not recognise `__volatile__`.** It matched
  `asm`/`__asm__` followed by `volatile`, but not by `__volatile__` — the
  reserved spelling C89 sources have to use. Embedded assembly written the
  ordinary way passed the clean-source gate **silently**. This is the gate the
  whole policy rests on; until now nothing had written asm that way.
- **The patch scanner attributed every added line to one function.** It used the
  single top-level `functionName`, which is `undefined` in a repo-wide sweep, so
  no allowlist entry could ever apply to a newly added line. An allowlisted
  construct failed the gate the first time its own file was edited. Added lines
  are now attributed to the function whose file they are in.
- **The patch scanner policed documentation.** Any note or retro that quoted
  `__asm__` failed the gate on the added line, so the repository could not write
  down the thing the policy is about — this retro tripped it. Construct bans now
  apply to `src/**.c` and `include/**.h` only, which is what the per-file scan
  already did.
- **`triage.ts`'s `asm-dead` detector read a branch's first operand as a
  destination**, so `bne $v0,$0,$L9` looked like a redefinition of `$v0` rather
  than a read of it. It reported this function's live asm output as dead — a
  blocker, on a 44/44 match. It now uses `BRANCH_MNEMONICS`.

The first three all point the same way: a prohibition that has never been
exercised is not known to work. Three of the four failed open — they let the
forbidden construct through, or blocked the record of it — and only the fourth
was noisy.

## Method note

Two failures worth recording, both about method rather than the compiler.

First, two long stretches went into hand-rolled variant sweeps in a scratch
directory when `searchSourceShapes` would have enumerated the same product with
artifacts, policy checks and ranking. Worse, the one search that was run through
the tool was pointed at the guard when the session's own evidence — two shapes
that flipped the choice, both in the post-call tail — said the lever was
elsewhere. The tool is fully steerable; it was steered badly.

Second, and larger: brute force was argued against three times before being
attempted, including with an invented figure (`10^6`, asserted rather than
computed, and wrong by two orders of magnitude against the tooling's own
measured axes). The actual enumerable space was 1,057,675 and took five minutes.
The decisive result of this session — a hard negative over a complete space,
plus 13,368 positive examples — came from finally running it. When a residual is
small and the space is a partition problem, count the space before arguing about
it, and prefer an exhaustive sweep with a cheap exact filter over any amount of
reasoning about which axis matters.
