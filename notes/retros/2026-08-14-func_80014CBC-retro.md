## The three levers that ended it (all verified by ablation this session)

1. **BLKmode struct stack parameters are the assign_parms lever.** A 4-byte
   `struct { u_char b[4]; }` parameter stays BLKmode on strict-alignment
   MIPS (align 1 < SImode's 32), so `assign_parms` leaves a stack parameter
   in its incoming slot with **no entry-block copy insn**. Declaring arg4
   and arg5 this way deleted the two `r85/r86 = mem` parameter loads from
   block 0's RTL. Everything else flowed from that:
   - arg4 reproduces the target's two lazy `lw v0,80(sp)` loads for free;
   - arg5's single register load becomes an ordinary C statement
     (`a5 = *(s32 *)&arg5;`) placeable *below* the arg1 home-store carrier,
     which turns the carrier→load relation into a true dependence
     (store-then-load) instead of the anti-dependence that had pinned the
     load above the store in every previous frame. This was the note's
     predicted "TU-context that changes assign_parms behavior."

2. **The stream position of a web's copy insn is movable by splitting the
   web in C.** The arg2 parameter copy (`move s6,a2`) could never sink below
   the address-sum at a sched1 tie: release ties resolve by original RTL
   position and a parameter copy's UID (8) loses to any statement. Routing
   all uses through a second variable (`len = arg2;` placed after the
   address asms) makes the surviving copy carry the statement's late RTL
   slot; the dead parameter copy is deleted. The split web's shorter live
   range then needs re-tuned reference counts (dummy asm inputs), but the
   *schedule* is finally reachable.

3. **Dependence gating with dummy asm operands.** sched.c schedules
   bottom-up; an insn is released when its successors are placed, and the
   second scheduler's late ties sort by descending sched1 output position.
   Where a value had to *lose* specific ties, the fix was never its own
   spelling but a manufactured successor:
   - the carrier's `"r"(len), "r"(result)` inputs hold the arg2 copy and
     the result zero-init out of the store's release window;
   - the fused `lui/addiu` literal asm takes a dummy `"r"(arg0)` input, so
     the arg0 entry copy gains it as a successor and releases one cycle
     after it — the target's `sw s5/move s5` above `lui/addiu` order;
   - the recursion's arg1 reload is written as a plain C read of the home
     slot (`*(s32 *)((char *)&arg4 - 12)`), giving the scheduler an
     ordinary load it can place like the original's reload-born one.

## Mechanisms measured on the way (general, reusable)

- **Asm insns never win hazard-class ties.** `potential_hazard` boosts come
  from function units; `recog_memoized` fails on asms, so an asm store can
  never beat a real store, load, or even a move at a priority tie. Real
  store placement must come from dependence gating, never class.
- **An opaque asm `"=m"` output may-aliases every sp-slot access whose RTL
  precedes it** — including assign_parms parameter loads. The resulting
  anti-dependences are unfixable from the store's side; remove the loads
  (BLK parameters) instead of fighting the alias.
- **`(mem (lo_sum ...))` asm operands are a post-reload trap:** the
  address register's dest-tie at the sum recreates a clobber, and the
  resulting anti-dependence pins the asm above the sum regardless of
  pseudo-level freedom.
- **Non-volatile asms float across calls** (no call dependence) and their
  empty `#APP` regions eat maspsx's reorder-mode nops when they land after
  a `jal` or inside a load-delay gap; `volatile` makes an asm a full
  scheduling barrier that stays where written. Use volatile for placement,
  plain for dataflow-pinned carriers.
- **Loads launch consumer-placement + latency cycles later** in the
  bottom-up queue. A lone-ready insn is *forced* into the stall gap (the
  carrier kept landing one slot low until the table-load dependence held it
  back one more cycle).
- **cse's commutative canonicalization places a constant-equivalent operand
  second, unconditionally** (`fold_rtx`'s final swap block), so
  `base + scaled` as a standalone C sum can never emit `addu v1,v1,v0` with
  the symbol side first; only memory-context sums (or a literal asm) reach
  that operand order.
- **Duplicate same-register inputs within one asm are not counted** by the
  flow ref-counter; inputs on *different* asms each count. Ref pumps and
  their floor_log2 boundaries (4→8→16 refs) are the allocno-priority
  levers; live-length pumps need real (live-output) insns inside the
  target web's window and nothing else's.
