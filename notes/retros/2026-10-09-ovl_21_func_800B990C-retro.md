## 1. The offset is an induction variable the compiler made

The target keeps the record offset in `$s3`, and two details show that loop.c
created it:

- **Prologue order.** `move s3,zero` is scheduled after the hoisted
  invariants (`lui s5,%hi(D_800C0448)` and the `D_800BCAD8` address in
  `$s6`). Strength reduction emits a giv's initialisation before the loop
  start after `move_movables` has placed the hoisted insns there. An offset
  written in the source is initialised with `i`, ahead of them.
- **The skip arm.** `li s3,0x108` sits beside `li s2,1`. loop.c accepts a
  constant set of a biv in an innermost loop (`loop.c:6012`), and the reduced
  giv receives the constant times its multiplier.

Every attempt in the parked session carried m2c's hand-written `off`
variable. It produced the prologue in the wrong order, and none of its
search grammars can turn a written offset into an index.

**Transfer:** if an offset register's zero init lands after the hoisted
invariants, and a constant set of the counter is paired with a constant set
of the offset, the offset is a strength-reduced giv. Index by the counter and
write only `i = 1`.

## 2. One record, three address shapes

The target forms addresses into record `i` in three ways:

| access | target | mechanism |
|---|---|---|
| s32 word at +0x14 | `(base + 0x14) + giv`, then `lw 0` | `expr.c:6497` adds the field offset to the base first |
| s16 fields at +0x18 / +0x2E | `(base + giv)`, then `lh 0x18` / `sh 0x2E` | that rule's alignment test fails, so the offset stays a displacement |
| position argument at +0x1A | `(base + 0x1A) + giv` | no field access through this record type gives it |

The `expr.c:6497` rule adds the constant bit position to the base before the
scaled index only when all of these hold:
- the reference is an array member of a BLKmode object;
- the bit position is a multiple of the field size;
- the object's alignment, as computed by `get_inner_reference`
  (`expr.c:4962`), equals the field mode's alignment.

The alignment is taken from the array element type outward. A record that
holds an s32 is 4-aligned, so only a 4-aligned s32 field qualifies. A
halfword at +0x1A could only qualify through a 2-aligned record. For BLKmode
the mode alignment is one bit (`machmode.h`), so a struct-typed field never
qualifies.

In the committed form, the position pointer is taken from record 0 just
before the call: `pos = (u8 *)blk->recs[0].unk6`, then
`pos + i * sizeof(Ovl21C0448Record)`.

**Transfer:** an address formed as `(base + field) + index` comes from an
array member of a struct, with a field whose mode alignment equals the
record's alignment. A narrower field of the same record that keeps its
offset as a displacement shows the record is more strictly aligned than that
field.
