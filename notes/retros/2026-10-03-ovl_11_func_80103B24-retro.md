# ovl_11_func_80103B24 — identical updates, distinct compiler paths

**Outcome:** clean C matches all 55 relocated words with an allowlisted
`-fno-cse-skip-blocks` override. `make check` and the function-scoped source
policy pass.

## The problem in the original bytes

The function checks `D_80127428 == 3`, computes a signed difference between
`D_8006C838 + 0x5224` and `D_8012CF20`, and, when it is nonzero, adds that
difference to the work-area word at `+0x49C8`. It then writes the current
`D_8012CF20` to `+0x5224` and copies six halfwords into a selected row of the
work area's `+0xE522` table.

The two updates are mathematically identical but physically separate:

```asm
bne   v1,a0,exit
 move a2,a3                 # the two work-area bases have the same value
...
blez  v1,not_positive
 move t1,a0
lw    v0,0x49C8(a2)
addu  v0,v0,v1
j     join
 sw   v0,0x49C8(a2)
not_positive:
bgez  v1,join
 nop
lw    v0,0x49C8(a3)
addu  v0,v0,v1
sw    v0,0x49C8(a3)
join:
```

Thus positive and negative differences each perform one `lw`/`addu`/`sw`,
zero performs none, and the positive path jumps over the negative path.
The `$a2 = $a3` delay-slot copy proves that their effective addresses are
identical. A candidate with one combined update has the right result but not
the target's instruction population, control flow, or register webs.

## Why the initial readings were misleading

- Straightforward `if (delta > 0) ... else if (delta < 0) ...` under baseline
  flags compiled to 49 instructions: GCC's CSE made the equivalent updates a
  shared branch body. Separate independent `if` statements retained two
  stores, but lacked the target's jump and pointer-copy structure. This was
  a population/CFG problem, not one to fix by scheduling or register naming.
- Applying `-fno-cse-skip-blocks` to the first natural candidate gave 54/55.
  It recomputed the global's low address with `addiu $a2,$a1,%lo(...)` where
  the target copies its existing base with `move $a2,$a3`. The flag fixed one
  pass decision but not the source's pointer provenance.
- A saved-pointer variant had exact instruction population and schedule but
  copied the pointer too early and inverted the `$a2`/`$a3` allocation. Its
  26,880-coordinate source closure did not fix that *particular* variant;
  the result said nothing about every other clean-C representation.

## The source-web correction

The winning source keeps an original pointer and a saved copy, then gives the
subtraction and both updates different source-variable histories:

```c
v = (ViewB24 *)&D_8006C838;
saved = v;
/* select row; return unless D_80127428 == 3 */
p = v;
v = saved;
delta = v->field_5224 - D_8012CF20;
if (delta > 0) {
    p->field_49C8 += delta;
} else if (delta < 0) {
    p->field_49C8 += delta;
}
```

Writing **both** updates through `p` looks odd if one transcribes the target
registers as C variables: the target uses `$a2` in one arm and `$a3` in the
other. Those registers hold the same address, and GCC's intervening passes
are free to assign and reuse either. The source is verified by compiled bytes,
not by a guessed register-to-variable mapping. The complete source also
retains a separate work-area address for the table-writing tail.

The decisive experiment was a finite grammar crossing pointer assignment
and use sites (1,512 candidate shapes), beyond the earlier prologue-only and
saved-pointer grammars. Its cc1-only quick ranking reported **no exact
candidate**, so that report was not treated as a proof. Inspecting the
emitted assemblies for two `%lo(D_8006C838)` address formations, the late
`move $a2,$a3`, and separate stores narrowed them to ten promising shapes.
Running the relocated-byte residual oracle on the candidate labelled
`v000004` returned `EXACT` (55/55). The preserved search is at
`build/sourceShapeSearch/ovl_11_func_80103B24/deef6c38bb4c140e/`.
Using the already-matched siblings' signed `s16 D_8012CF10[7]` declaration
and casting each read to `u16` kept the target's `lhu` and preserved the
match in the integrated C.

## Flag evidence and limits

For the integrated source, the flag matrix gives baseline 49 instructions
(10/55 masked) versus `-fno-cse-skip-blocks` **55/55 words**. The original
bytes retain separate sign-guarded read/modify/write arms at the same
address and the positive arm's jump; that is the structural symptom. Matched
neighbors `ovl_11_func_801037EC` and `ovl_11_func_80104394` both remain exact
when compiled with the flag, so they provide no contrary same-region witness.
The override and its source-policy allowlist entry record this evidence. This
proves the flag is needed **for the matched source**, not that every possible
C source under baseline flags is impossible.

## Transfer

When two guarded arms update an equal address, derive their CFG and address
identity from the original bytes before folding them together in C. If the
baseline candidate collapses the arms, treat the count as an early CSE/CFG
residual. Probe the flag, but do not adopt it on a near miss: a low-sum in
place of a pointer copy is a separate source-web problem. Vary which alias
feeds the subtraction and *each* store, not merely variable spelling. Finally,
verify plausible generated sources with the relocated-byte oracle even when
a cc1-only search score says `no exact`.
