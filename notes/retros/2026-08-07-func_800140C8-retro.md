# Retro: func_800140C8 — five instructions that were really one object copy

Final state: byte-verified 29/29, full build green, clean C89, baseline flags,
and no policy exception. The load-bearing reconstruction is only this:

```c
PadPortPair ports;

ports = D_8005E2AC[0];
```

The difficult part was not discovering what the function does. That was clear
early: copy the two pad port IDs to a local object, select one by `arg0`, poll
it, and align its actuators when stable. The difficult part was recovering the
**operation boundary** the original compiler saw. We spent most of the search
treating the first ten machine instructions as independent scalar loads,
stores, address calculations, and scheduling decisions. GCC had treated five
of them as one `movstrsi_internal` block-copy instruction.

## 1. Why this became difficult

### 1.1 The scalar decompilation was semantically right and structurally wrong

The obvious reconstruction was:

```c
base = D_8005E2AC;
tmp0 = base[0];
tmp1 = base[1];
ports[0] = (s8)tmp0;
ports[1] = (s8)tmp1;
```

That has the right observable behavior, memory offsets, constants, calls,
frame size, and final instruction count. Its entire suffix after the initial
copy matched. Depending on the metric it reached 22/29 by masked LCS and 19/29
by exact index. This made the residual look like a small address-CSE,
allocation, or scheduling problem rather than a wrong source-level operation.

The diagnosis of the scalar candidate was technically correct. Initial RTL
materialized one `D_8005E2AC` base. CSE then replaced the offset-zero load with
`mem(lo_sum(high, symbol))`, while the offset-one load continued to use the
base pseudo. That changed web parity and consequently the registers and
prologue schedule.

The mistake was the question we asked next: **how can clean C stop CSE from
making that substitution?** The better question was: **why does the target
look like GCC's block mover rather than two scalar assignments?**

### 1.2 m2c erased the aggregate boundary

The first-pass decompilation represented the local bytes independently:

```c
s8 sp10;
s8 sp11;

sp10 = D_8005E2AC.unk0;
sp11 = D_8005E2AC.unk1;
```

That is a reasonable semantic rendering of the instructions, but it cannot
recover whether the source used two field assignments or copied a containing
object. Once those statements became the working model, every later
experiment inherited scalar semantics.

We did test arrays, structs, unions, field accesses, pointer holders, and local
aggregate layouts. Almost all still read and wrote the members separately.
The missing axis was not **aggregate type versus array type**; it was
**whole-object assignment versus scalar member assignment**. Testing a struct
layout is not testing an aggregate copy.

### 1.3 A nearly exact suffix pulled the investigation downstream

Because both streams had 29 instructions and all semantic inventories were
clean, it was tempting to treat the mismatch as a late-pass residual. That led
to allocator models, scheduler analysis, source-order changes, dead-reference
experiments, and hundreds of clean scalar forms. These tools accurately
explained the scalar program we gave the compiler. None could create the
missing block-copy RTL operation.

The 707-candidate residual search is the clearest example. It was exhaustive
over its grammar, not over C. The grammar varied scalar representations of the
copy, so exhaustion proved only that the scalar family was spent. We treated
that result too much like evidence that ordinary C was spent.

### 1.4 The target packet hid its compiler boundary

The target prefix is:

```asm
lui    v0,%hi(D_8005E2AC)
sw     ra,32(sp)
sw     s1,28(sp)
sw     s0,24(sp)
addiu  a3,v0,%lo(D_8005E2AC)
lb     v1,0(a3)
lb     a1,1(a3)
sb     v1,16(sp)
sb     a1,17(sp)
```

At machine level, the `addiu/lb/lb/sb/sb` region appears to be five
instructions available for ordinary scheduling and allocation. In GCC RTL it
is one instruction with a declared length of 20 bytes and four scratch
clobbers. The post-reload scheduler moves that one packet; the final assembly
printer expands it into the five instructions. Machine-instruction analysis
therefore overcounted the number of independent decisions that source shape
had to reproduce.

### 1.5 Nearby real asm made the wrong precedent psychologically available

This family is close to functions that use the genuine `CAPTURE_RA` debug-hook
idiom. When clean scalar forms repeatedly failed to preserve the shared base,
it was natural to ask whether this was another source macro invisible to C.
Diagnostic barriers and pinned-register experiments could improve the score,
which made the idea feel plausible.

The target never had the relevant fingerprint: no non-stack `$ra` store, no
hard-register read-before-definition, and no unexplained machine operation.
The read-before-definition scanner and source-policy gate were right to reject
that direction. The eventual solution required no analogue of `CAPTURE_RA`.

## 2. The actual compiler mechanism

The matching declaration gives the global an unknown total size while naming
the copied unit:

```c
typedef struct PadPortPair {
    s8 port0;
    s8 port1;
} PadPortPair;

extern PadPortPair D_8005E2AC[];
```

The incomplete outer array is load-bearing for address selection: GCC cannot
classify the complete object as a known two-byte small-data object. The record
itself is exactly two bytes with alignment one, which controls block-move
lowering.

Whole-object assignment enters initial RTL as a BLKmode move:

```text
(set (mem/s:BLK destination)
     (mem/s:BLK source))
(clobber scratch) x4
(use 2)                         /* byte count */
(use 1)                         /* alignment */
```

By `.cse`, the relevant source is:

```text
(mem/s:BLK
  (lo_sum:SI (reg:SI high)
             (symbol_ref:SI "D_8005E2AC")))
```

This corrects an important nuance in the early explanation: CSE does still
canonicalize the aggregate's address to a `lo_sum`. The win is not that CSE
never sees the constant address. The win is that there is no independent
scalar offset-zero `MEM` to emit directly.

The operation remains `movstrsi_internal` through `.dbr`. Its machine
description declares four early-clobber integer scratch registers and returns
`output_block_move`. In this case global allocation assigns those scratches
as `$v1`, `$a1`, `$a2`, and `$a3`. The output routine then does two special
things:

1. It sees a `LO_SUM` source and consumes the last scratch (`$a3`) to emit:

   ```asm
   addiu a3,v0,%lo(D_8005E2AC)
   ```

2. It sees two bytes at alignment one, so it chooses two byte loads followed
   by two byte stores:

   ```asm
   lb v1,0(a3)
   lb a1,1(a3)
   sb v1,16(sp)
   sb a1,17(sp)
   ```

`$a2` is a declared scratch that this two-byte case does not need to print.
This one backend pattern explains all of the facts that looked independent:

- why both loads share one low-address base;
- why the low `addiu` is separated from the `lui` by the prologue saves;
- why the two loads are contiguous and precede both stores;
- why the values land in `$v1` and `$a1`;
- why the source base lands in the otherwise surprising `$a3`;
- why no scalar CSE source shape or allocation phantom could reproduce the
  target web structure.

The emitted `lb` instructions are also not reliable evidence that the record's
fields were semantically signed. `output_block_move` hardcodes `lb` for an
alignment-one byte chunk because only the low byte is stored. Here `lb` is a
block-mover fingerprint before it is a C signedness fingerprint.

## 3. Detours and what each one actually established

### Prototype and frame work

Correcting `PadGetState` to its SDK one-argument prototype was necessary. The
old multi-argument declaration kept extra values live and produced 30
instructions. The correct prototype reduced the candidate to the target's 29
instructions and isolated the prefix.

The frame investigation also found a real tooling error. `sp+0x10` and
`sp+0x11` are an address-taken two-byte local, not fifth and sixth outgoing
arguments. The 0x28 frame consists of the ABI-minimum 0x10 outgoing area, an
8-byte padded local region, and three saved registers. The current frame-map
heuristic still reports a false 0x18 outgoing area even on the exact source;
the research note now records this counterexample, but the detector needs to
be fixed.

Caller evidence left `$a1 = &D_8005E3E8` at the call, which made a hidden
second parameter plausible. It was still unread by the callee and therefore
binary-invisible. Trying one through four declared parameters was a fair ABI
check, but it could never repair the copy packet.

### Shared-base experiments

Pointer copies, reused incoming parameters, address-taken locals, pointer
unions, inline helpers, volatility, integer casts, and related-address forms
all tested whether source metadata could suppress the scalar substitution.
They mostly collapsed to the same scalar RTL.

The most informative negative and positive controls were:

- `-mno-split-addresses` preserved a shared base and proved address splitting
  was involved, but did not reproduce the target registers or schedule. It
  modeled the symptom at the wrong compiler layer and was correctly rejected
  as a TU flag hypothesis.
- Biasing the source base by -1 and loading offsets 1 and 2 preserved both
  loads through one base. This showed precisely that scalar CSE substitutes a
  bare offset-zero address but leaves nonzero related addresses alone. It also
  produced the wrong relocation addend and offsets, so it was diagnostic, not
  a solution.
- Empty/operand asm barriers reached a better score by perturbing CSE and
  allocation. They demonstrated sensitivity, not provenance, and were
  unshippable under clean-source policy.

### Sibling evidence

`func_80013B04` contains the same shared-base `lb/lb/sb/sb` copy from
`D_8005E2AC` into local bytes. That clue was correctly identified but initially
interpreted as evidence for a shared pointer/declaration or macro. It is
stronger evidence for a shared **record-copy idiom**. When that sibling is
decompiled, its prefix should be tested first as the same `PadPortPair` object
assignment rather than reconstructed as two scalar fields.

## 4. What went well

1. **Policy prevented a false success.** Register pins and embedded asm were
   never promoted, despite improving local scores.
2. **The SDK prototype check removed a real extra instruction.** It reduced
   the problem to one coherent residual instead of mixing arity/liveness with
   copy lowering.
3. **Inventory and exact instruction count established semantic proximity.**
   They showed the function body was understood even though the operation
   family was wrong.
4. **Compiler dumps eventually gave a complete causal chain.** The match is
   not merely empirical: `.rtl`, `.cse`, `.greg`, `movstrsi_internal`, and
   `output_block_move` account for every instruction and register in the
   prefix.
5. **Sibling/TU research was productive.** It identified the shared pad data
   group and ruled out treating this function in isolation.
6. **Final verification was appropriately strict.** Exact function diff,
   linked relocations, full build, scope, and source policy all passed.

## 5. What should change in the playbook

### Recognize candidate block-copy packets before scalar search

A short sequence with these properties should trigger an aggregate-copy test:

- adjacent source offsets and adjacent destination offsets;
- all loads occur before all stores;
- equal copied width on each side;
- an address-taken local destination;
- a source `lui` feeding a low-address scratch used by every load;
- total packet length matching a `movstr*` machine pattern.

For this target, a two-field struct assignment should have ranked ahead of
volatile pointers, allocator phantoms, or scheduler-state search.

### Treat source operation family as a separate axis from type shape

A search that includes `struct` but only emits member-wise assignments has not
searched aggregate copies. Source grammars should distinguish at least:

- member-by-member copy;
- whole-struct assignment;
- fixed-size block-copy idioms where period headers/compiler support them.

### Ask whether several machine instructions are one RTL instruction

Before modeling a compact load/store packet as five scheduler nodes, inspect
the target machine descriptions and output functions. A `define_insn` with a
multi-instruction length can make machine-level order and register choices
look much freer than they are. Scheduler and allocator searches cannot solve a
residual whose target packet boundary is missing from the candidate.

### Interpret exhaustive search results narrowly

“707 variants, no match” means “no match in this 707-member language.” Stable
failure at the same first pass and same web-parity defect should prompt a new
semantic axis, not a larger permutation of the old axis.

### Fix the frame decomposition detector

The detector must subtract identified locals/spills before treating the region
below save slots as outgoing argument space. Address formation to `sp+0x10`,
stores there, and later indexed reloads are positive local-object evidence.
This exact matched function should be a regression fixture.

### Add backend packet hints to diagnostics

A useful diagnostic would map a target subsequence to vendored machine
patterns such as `movstrsi_internal`, including declared length and scratch
count. Even a heuristic warning — “five target instructions may be one
20-byte block-move RTL insn” — would have redirected this investigation much
earlier.

## 6. The efficient path in hindsight

The shortest evidence-driven route would have been:

1. Use the SDK prototype: `PadGetState(int)`, `PadSetActAlign(int, u8 *)`.
2. Classify `sp+0x10..0x11` as one address-taken two-byte local object.
3. Notice the target loads both source bytes before storing either one.
4. Search the MIPS backend for a two-byte block move and inspect
   `movstrsi_internal`/`output_block_move`.
5. Declare a two-byte, alignment-one record and the global as an incomplete
   array of that record.
6. Write one whole-object assignment and compile.

That path would have matched on the first aggregate-copy experiment. The main
lesson is not merely “try structs.” It is:

> Preserve the source-level object operation. Five machine instructions can be
> one compiler instruction, and scalarizing that instruction can make every
> downstream register and scheduling fact unreachable.
