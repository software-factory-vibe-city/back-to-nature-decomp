# Retro: func_80016B7C (SOLVED 2026-08-10, clean C, 35/35)

Sprite data size calculator in the sprite-renderer family. Searches for
matching entries via `func_80015B24`, loads tile/image data via
`func_8001782C`, and returns the size truncated to a multiple of 4 plus a
32-byte header offset. Solved from an `INCLUDE_ASM` stub: `diffFunc` 35/35,
byte-identical in the linked binary (relocations included), no
pins/asm/overrides.

Final source (`src/func_80016B7C.c`):

```c
#include "common.h"

s32 func_80015B24(s32 *arg0, s32 *arg1, u16 arg2);                    /* extern */
s32 func_8001782C(s32 *arg0, s32 arg1, u16 arg2, s16 arg3, s16 arg4); /* extern */

s32 func_80016B7C(s32 *arg0, s32 arg1, s32 arg2, s32 arg3, s32 arg4) {
    s32 found;
    s32 size;

    found = func_80015B24(arg0, (s32 *)arg0[6], arg1);
    size = func_8001782C((s32 *)arg0[6], arg2, found, arg3, arg4);
    return size / 4 * 4 + 0x20;
}
```

> **Revision note (2026-08-10, second pass).** The first version of this
> retro reached the right answer but recorded a wrong *explanation* of it —
> a nonexistent `$a4` register, bad frame arithmetic, and two takeaways that
> were false or backwards. Those are corrected below. The correction itself
> is a data point: a retro that ships a plausible-sounding mechanism is
> worse than no retro, because the next agent inherits it as fact.

## Phase 1 — undersized signature, phantom inline asm (~20 wasted variants)

The research note (`notes/research/func_80016B7C-research.md`) stated the
function has **3 register args and no stack args** (line 9), and also
misattributed the first call's arguments (line 48: `$a0 = lw(0x18($s2))`).
Both claims were unverified. Variants were built on undersized signatures
(the last one left in the tree carried 4 parameters). The function actually
has **5**.

### The cascade of wrong assumptions

**1. `lw $s0, 0x40($sp)` — misread as "caller's return address"**

```
addiu sp,sp,-0x30
...
lw    s0,0x40(sp)   <- what is this?
jal   func_80015B24
addu  s1,a3,$0      <- delay slot: s1 = a3
```

This was read as the function reaching for its caller's saved `$ra`, and
since C cannot express that, the variant reached for inline asm:

```c
__asm__ volatile("lw %0,64($29)" : "=r"(caller_ra));
```

**The arithmetic never supported that reading.** The frame is 0x30, so
`0x40($sp)` is `caller_sp + 0x10` — the O32 fifth-argument slot, and
nothing else. The caller's actual saved `$ra` lives at `0x84($sp)` in
`func_80016C08` (`build/functions/func_80016C08.s:13`), which is
`func_80016B7C_sp + 0xB4`. The two slots were never close, and there was
no coincidence to be fooled by.

**2. `addu $s1, $a3, $0` in the delay slot — misread as "callee side-effect"**

`$a3` is the fourth parameter. The delay slot is the compiler saving it
into a callee-saved register before the `jal` clobbers `$a3`.

**3. Frame 0x30 — misread as "extra padding"**

The frame decomposes as **24 bytes of outgoing argument area + 20 bytes of
saved registers** (`$s0`–`$s3` + `$ra`), rounded to 48. The 24-byte
argument area is the load-bearing part: it is sized by the widest outgoing
call, and `func_8001782C` takes 5 arguments. The undersized source
compiled to frame 0x20 = 16-byte argument area (4-arg calls) + 16 bytes of
saved registers.

This is exactly the diagnostic that was already written down, about this
same family, in the sprite-renderer debugging notes then living in
`notes/file-groupings.md`: *"GCC 2.95 frame size is a strong signal for
argument count... If your compiled frame is 0x68 but the target is 0x70, you
have too few declared arguments."* It was in the repo, about these very
functions, and went unread — which is why it is now a detector
(`tools/agent/triage.ts`) backed by
`notes/research/frame-size-arity-diagnostic.md` rather than a paragraph
buried in a membership ledger.

### Correcting the ABI claim

The first version of this retro explained the stack load as *"GCC 2.95
saves `$a4` to the stack during the prologue and reloads it."* **There is
no `$a4` in MIPS O32** — the argument registers are `$a0`–`$a3`. The fifth
argument is stored by the **caller** and only ever loaded by the callee.
Both call sites show the store plainly, in the `jal` delay slot:

```
    lh   $a3, 0x4($s1)
    lh   $v0, 0x6($s1)
    jal  func_80016B7C
     sw  $v0, 0x10($sp)      <- fifth argument
```

(`build/functions/func_80016C08.s:130` and `:162`.)

### Why inline asm felt right (and why it was wrong)

`func_80016054`, a confirmed member of the same family, genuinely needs
embedded asm: `CAPTURE_RA` stores the *live* `$ra`, which C cannot read.
The surface similarity ("a function in this family, doing something with
the stack near `$ra`") was enough to trigger the association.

Three independent signals said no, and none of them were checked:

- **The null-case rule**, already in the playbook
  (`notes/research/caller-capture-debug-hook.md`, "Scheduling lessons"):
  *compile the function with no asm at all and read the natural output
  first*. That single step yields frame 0x20 against a target 0x30 — the
  arity signal — before any variant search begins.
- **The asm's output was dead.** GCC assigned `caller_ra` to `$2`, the
  following `jal` clobbered it, and `andi $6,$2,0xffff` then consumed the
  *call's* return value. The asm computed nothing that survived. An asm
  block whose output is provably unused is not explaining the target.
- **The source-policy gate.** `func_80016B7C` has no entry in
  `.pi/autodecomp.json` `sourcePolicy.allowlist`. Per the repository guide,
  embedded asm is not a valid solution without an explicit exception, so
  every asm variant was unshippable by construction — regardless of score.

**Lesson:** the CAPTURE_RA signature is narrow and checkable. It is
`sw $ra, 0x0($reg)` with a **non-`$sp` base**, preceded by
`addu $8,<reg>,$0`, before the first `jal`
(`notes/research/caller-capture-debug-hook.md`, "Byte-level signatures").
This target's only `$ra` traffic is `sw $ra, 0x28($sp)` — an ordinary
frame save. Match the signature before invoking the precedent.

## Phase 2 — correct signatures, everything falls out

Two independent fixes were needed, and it is worth keeping them separate
rather than crediting the arity insight with all of it:

**Fix A — this function's arity** (5 parameters, `arg4` on the stack):

| target feature | undersized model | 5-param model |
|---|---|---|
| `lw s0,0x40(sp)` | caller's RA (needs asm) | `arg4` load (natural) |
| `addu s1,a3,0` | callee clobber capture | `arg3` save (natural) |
| frame 0x30 | unexplained padding | 24B arg area + 20B saved regs |

**Fix B — the callee prototypes** (independent of Fix A; these would have
been needed at any arity):

| target feature | cause |
|---|---|
| `andi a2,a1,0xffff` | `u16` parameter on both callees |
| `sll/sra` sign-extends | `s16` parameters 4 and 5 of `func_8001782C` |
| 5-arg outgoing call | `func_8001782C` reads `lh $t2, 0x30($sp)` — its own 5th arg |

With both fixes, the function matched on the first compile — no scheduling
fight, no allocation fight.

## Takeaways for the playbook

1. **Cross-check arity from both sides; they answer different questions.**
   The callee's frame tells you what it *consumes* (incoming stack loads
   at `$sp + framesize + 0x10` and above; outgoing argument-area width).
   The caller tells you what it *supplies* (stores to `0x10($sp)`+ before
   the `jal`, often in the delay slot). Here the caller was unambiguous and
   correct — reading it would have ended the investigation on turn one.
2. **In O32, a load from `$sp + framesize + 0x10` or above *is* an incoming
   stack argument.** This is determinate, not ambiguous — it is an arity
   oracle, not a trap. Do the frame arithmetic before theorizing: subtract
   the frame size and see where the offset lands in the caller's frame.
   Argument slots start at `caller_sp + 0x10`; the caller's own saved `$ra`
   sits high in *its* frame and will not be anywhere near.
3. **Run the null case before reaching for asm.** Compile with no asm at
   all and read the natural output. Frame-size mismatch against the target
   is an arity signal that costs one compile to obtain.
4. **If a solution requires a source-policy exception you don't have,
   stop.** An asm variant for a function absent from
   `.pi/autodecomp.json`'s allowlist cannot ship. Treat the missing entry
   as a signal that the premise is wrong, not as paperwork to file later.
5. **An asm block whose output is dead is not modeling the target.** Read
   the generated `.s`: if the value is clobbered before use, the asm is
   decoration and the real explanation is elsewhere.
6. **Research notes can propagate wrong facts.** This function's note
   asserted an arity and a call's argument mapping that were both wrong,
   and every downstream variant inherited them. Verify a note's structural
   claims against the assembly before building on them; correct the note in
   the same session.
7. **Natural parameter types solve masking and sign-extension.** `u16`
   parameters produce `andi 0xFFFF`; `s16` parameters produce
   `sll 16; sra 16`. Don't hand-write masks or casts when the callee
   prototype can express them.
8. **`x / 4 * 4` truncates toward zero; `(x >> 2) << 2` floors.** They
   differ for negative values, and the asm tells you which one the source
   used. The `bgez; addiu 3; sra 2` sequence is the compiler *correcting*
   the arithmetic shift so it truncates — i.e. it exists precisely to
   produce C division semantics rather than floor. If you see the `bgez`
   correction, the source wrote `/`; a bare `sra` means the source wrote
   `>>`. (C89 leaves negative-operand division implementation-defined;
   GCC 2.95 on MIPS truncates toward zero.)
