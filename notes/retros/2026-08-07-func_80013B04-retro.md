# Retro: func_80013B04 — a loop that was two loops, scored against an oracle that was not running

Status: byte-verified, relocations included, full build green. The masked score
went 78/116 -> 111/115 on the source fix; the last four differences were
relocation-display artifacts that the masked diff cannot adjudicate and that
resolve identically at link time. Only the byte oracle could settle them, which
required fixing the jump-table build gap in section 3.

The load-bearing change is structural:

```c
for (port = 0; port < 2; port++) {
    retry = 1;
    do {
        ...
    } while (retry == 1);
}
```

The previous source expressed the same behaviour as one flattened loop with
`continue`. Everything else about it was close to right.

## 1. What the agent concluded, and why it was wrong

The working file carried a careful, compiler-backed analysis ending in:

> gcse PRE places hoisted computations at EE[bb] (block end), never at loop
> headers for non-invariant expressions. No tested clean C source shape forces
> the precomputation to the loop header.
>
> DEFERRED: gcse PRE limitation is a proven compiler behavior unreachable from
> any tested clean C source shape.

Both sentences about GCSE are true. The conclusion does not follow, because
`port << 3` is only non-invariant **in a single loop**. The target is not one:

```
.L80013B50:                     <- outer header
    sll   $s2, $s1, 3                port << 3
    addiu $s6, $s1, 0x1              port + 1
    addu  $v0, $s5, $s1              &ports + port
.L80013B5C:                     <- inner header
    lbu   $a0, 0x0($v0)
    jal   PadGetState
...
    beq   $s3, $v0, .L80013B5C       back-edge: retry the same port
    bnez  $v0, .L80013B50            back-edge: advance to the next port
```

Two back-edges to two distinct headers. All three quantities are invariant with
respect to the inner retry loop, so ordinary loop-invariant motion puts them in
its preheader. No hoist has to be coaxed out of GCSE; the position exists for
free once the loop exists.

The measurement that settles it:

| source shape | `sll` count |
|---|---|
| target | **10** |
| flattened, one loop | 13 |
| nested | **10** |

The "3x extra sll" the file named as the blocking mechanism is an artifact of
the flattening. Restoring the nesting removed it and took the score from 78 to
111 of 115.

## 2. The search reported exhaustion over a dimension it never opened

The file recorded `~80+ variants, 18 categories`, and under LOOP STRUCTURE:
for-loop with `++port`, `while(1)` with `++port` at the end, goto-based, and
`do-while`. Four entries, all of them **single** loops. Nesting never appears.

The residual search said so plainly and it was read backwards:

```
RESIDUAL SOURCE SEARCH:
  Domain: 1 candidate (fixpoint). Switch/continue/break/for-loop frozen.
```

"Fixpoint" reads as *exhausted*. With the loop frozen it means *nothing in this
dimension was searched*. Loops are frozen deliberately — opening them makes the
domain unenumerable when the residual is large — so the search is behaving
correctly and reporting misleadingly.

This is the `func_800140C8` failure one level up. There the missing axis was
operation family: whole-object assignment versus member-wise. Here it is
control structure: nested versus flattened. Both times an exhaustive search
over a grammar that could not express the answer was read as evidence that
clean C was spent.

## 3. The oracle was never running

The more serious finding. Every one of the ~80 variants was scored on the
masked, relocation-blind LCS metric. The byte oracle was unavailable the whole
time:

```
BYTE VERIFY UNAVAILABLE: full build failed
mips-linux-gnu-ld: build/asm/data/800.rodata.s.o:(.rodata+0x6c):
    undefined reference to `.L80013BE8'
```

The switch compiles to a jump table. GCC emits its own into the object's
`.rdata`, correctly — its entries are `$L13,$L13,$L10,$L10,$L16,$L16,$L17`
against the target's `.L80013B94,.L80013B94,.L80013C70,.L80013C70,.L80013BE8,
.L80013BE8,.L80013C04`, the same shape. But the extracted `jtbl_8001005C` is
still emitted into `800.rodata.s`, still referencing labels that no longer
exist once the function is C, so the link fails.

`func_80013B04` is the first function in this project whose switch produces a
real jump table. `func_8001A8D0` has a switch, but its cases are sparse and
compile to comparisons. So the case has never been exercised.

Nothing surfaced this. The header reports "Best clean C: 78/116 (67.2%)" as
though it were ground truth. `notes/.../masked-diff-blindness` already warns
that the masked tools cannot see relocation-level differences and that the run
must finish on real bytes — but nothing checks that finishing on real bytes is
even *possible*.

### Why it had never been automated

Hand-adding the subsegment does not survive: `make split` runs five `--write`
generators over `configs/splat.yaml` before invoking splat, and they rewrite the
file. The `[0x944, .rodata, func_8001A8D0]` line that already existed was added
by hand in a commit named "more stuff" — no generator produced it, nothing
tested it, and `mergeFragments --write` deletes it outright. It survived only
because nobody had run that tool standalone since.

This is why it surfaced now rather than earlier, and the population explains
the rest. The game contains seven jump tables. Six belong to functions that are
still stubs:

```
jtbl_80010008 -> func_80011370  [stub]
jtbl_8001005C -> func_80013B04  <- this one
jtbl_800100B4 -> func_800183E0  [stub]
jtbl_800100DC -> func_8001A284  [stub]
jtbl_80010224 -> func_80020E58  [stub]
jtbl_80010378 -> func_80022B98  [stub]
```

Of 178 functions decompiled, exactly one had ever owned a jump table, and only
two of 466 sources contain a `switch` at all. This was the second occurrence
ever, not a late regression.

### The four bugs, and the gap that hid them

Detection, in `mergeFragments.ts`:

1. Tables whose entries are all `.L` internal labels were never registered —
   the parser required at least one target resolvable to a known symbol, and
   `.L` words were explicitly skipped. That is every C-owned table in practice.
2. The `.rodata` subsegment insert ran only for merge-group heads, so a
   function owning a table without absorbing a fall-through fragment got
   nothing.
3. The owner fallback filtered targets through the symbol table before using
   them, so it could never fire for the case in (1).
4. A "strip orphaned entries" path deleted `.rodata` entries with no
   re-insertion. Strip-and-re-derive is unstable by construction anyway: once
   an entry exists, splat routes that table into the owning object and stops
   emitting it into the extracted assembly, so the detector can no longer see
   what it just placed. The list is now merged, not re-derived, and an entry is
   dropped only when its function returns to being an INCLUDE_ASM stub.

Placement, in `patchSplatForLibs.ts` — the gap that made the above look
unfixable. Reaching the `[0x800, rodata]` line, it discards the whole rodata
region and regenerates it with `interleaveEntries`, a cursor walk that emits
library object chunks with `[cursor, rodata]` filler between them. Its data
model had exactly two things in that region: library chunks and monolithic
filler. A C-owned jump table is the same kind of thing — a ROM range supplied
by an object file — but had no representation, so correctly placed entries were
regenerated away and stranded after the library block, which splat rejects as
out of order.

The fix adds that third entry kind and folds the existing entries into the same
ordered walk, so the continuation segments fall out of the mechanism already
there. Detection stays in `mergeFragments`; placement stays here.

Verified idempotent across three consecutive `make split` runs.

The `.align 3` question turned out to be a non-issue: GCC's directive and the
target's 4-mod-8 table address coexist once the object owns the section.

## 4. What to build

Ordered by how much each prevents a repeat.

1. **Fail loudly when the byte oracle cannot run.** This is the whole retro in
   one item. A masked score reported without a working oracle is a number with
   no denominator. Any tool that prints a masked score should first check that
   the full build links, and say so when it does not, in the same breath as the
   score. Eighty variants were ranked against a proxy that nothing could
   confirm.
2. ~~**Generator support for C-owned jump-table rodata.**~~ Done — see
   section 3. The remaining five stub owners should now decompile without
   anyone touching `splat.yaml`, which is the real test of the fix.
3. **A loop-nesting triage detector.** Distinct back-edge targets separate the
   cases and need no source at all:
   ```
   flattened source:  both back-edges -> L22            one loop
   nested source:     back-edges -> L26, L27            two loops
   target:            back-edges -> .L80013B5C, .L80013B50   two loops
   ```
   Same shape as the backend-packet detector: target-side, runs on a bare stub,
   states a structural constraint the candidate must satisfy. It would have
   redirected this before the first variant.
4. **Name frozen axes in exhaustion reports.** "Domain: 1 candidate (fixpoint)"
   must read "control structure frozen — loop nesting not searched". The
   information is already computed; only the wording invites the wrong reading.

## 5. What went well

- The block-copy work landed. `addiu`/`lb`/`lb`/`sb`/`sb` reproduced exactly
  and never appeared in the residual, so the aggregate-copy tooling from the
  preceding function did its job on the first try.
- The compiler analysis was real. The GCSE dump reading was correct and
  specific; only the inference drawn from it was too strong.
- Policy held. No asm, no register pins, and the flag hypothesis was correctly
  refused: flagProbe found no fingerprint and baseline dominated every column.
- The file recorded what had been tried in enough detail that the gap was
  visible from the outside. The LOOP STRUCTURE list is what made "all four are
  single loops" obvious.

## 6. The shortest path in hindsight

1. Count distinct back-edge targets in the target. Two means two loops.
2. Write the nesting before anything else.
3. Confirm the byte oracle can run at all before ranking variants against it.
