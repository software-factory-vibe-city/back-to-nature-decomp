# Retro: func_80022F1C (SOLVED 2026-07-26, clean C, 49/49)

Expanded research case study (mechanisms verified against vendored GCC
2.95.2 sources):
`notes/research/func_80022F1C-shift-fusion-and-address-legitimization.md`.

Threshold-cascade function: looks up a `s16` in `D_80055988`, uses it to index
a 468-byte-strided structure at `D_8006C838 + 0x99EC`, then buckets the loaded
`u16` against six thresholds (5000/20000/30000/40000/50000/60000) returning
0–6. Solved in fresh mode from an `INCLUDE_ASM` stub: `diffFunc` 49/49,
`make check` byte-identical, no pins/asm/overrides. Session also found and
fixed a real bug in the pi extension's finalize scope gate (see last section).

Final source (`src/func_80022F1C.c`):

```c
#include "common.h"

s32 func_80022F1C(s32 arg0) {
    s32 idx;
    char *base;
    s16 val;
    char *ptr;
    u16 result;

    idx = (s16)arg0;
    base = (char *)&D_8006C838;
    val = D_80055988[idx];
    ptr = base + val * 468;
    result = *(u16 *)(ptr + 0x99EC);
    if (result < 5000)  return 0;
    if (result < 20000) return 1;
    if (result < 30000) return 2;
    if (result < 40000) return 3;
    if (result < 50000) return 4;
    if (result < 60000) return 5;
    return 6;
}
```

## Phase 1 — three semantic misreads (and ~10 wasted variants)

The first-pass reconstruction baked in three wrong readings of the target asm.
Fuzz variants v1–v10 then attacked *shape* problems that didn't exist — the
semantics were wrong, so no shape could converge. Best result: 4/49.

### Misread 1: `sll 16; sra 15` is not `>> 1`

```
sll a0,a0,16
sra a0,a0,15
```

Read as "sign-extend, then shift right 1" → source `D_80055988[(s16)arg0 >> 1]`.
Actually it is `sext16(arg0) * 2`: `(x<<16) >>a 15 == sext16(x) * 2` exactly
(the low 16 bits of `x<<16` are zero, so the arithmetic shift by 15 keeps
bit 0 clear). The `sra 15` is **combine.c merging the sign-extension
(`sra 16`) with the s16-element scaling (`sll 1`)** — the array index is just
`(s16)arg0`. The `>> 1` version made combine produce `sra 14` instead —
visible in every early variant and correctly read as "shift amounts combine",
but the fix was semantic (drop the phantom `>> 1`), not structural.

**Lesson:** decode shift pairs arithmetically before writing C. `sll N /
sra N−k` around an array access is usually the sign-extension fused with
element scaling, not an extra source-level shift.

### Misread 2: the multiply chain is ×468, not ×28

```
sll  v0,v1,3     v0 = 8v
subu v0,v0,v1    v0 = 7v
sll  v0,v0,2     v0 = 28v
addu v0,v0,v1    v0 = 29v      <- first pass stopped reading here
sll  v0,v0,2     v0 = 116v
addu v0,v0,v1    v0 = 117v
sll  v0,v0,2     v0 = 468v
```

Strength reduction for ×468 = 4·117 = 4·(4·29+1) needs **seven**
instructions. The first pass evaluated only the first three and wrote
`val * 28`. **Lesson: always evaluate the whole chain to a fixed point**
(each `sll`/`addu`/`subu` until the result feeds a non-chain instruction).

### Misread 3: `sltiu` sign-extends — `ori` immediates are `C−1`

```
sltiu v1,a0,0x1388         constants < 0x8000: direct sltiu (5000, 20000, 30000)
...
ori  v0,zero,0x9C3F
sltu v0,v0,a0              tests 0x9C3F < a0  <=>  a0 >= 0x9C40 (40000)
```

On MIPS, `sltiu` **sign-extends** its immediate, so it can only encode
constants 0..32767. For `x < 40000` GCC must emit `ori C−1; sltu` (the
reverse test `C−1 < x`). The first pass copied the `ori` immediates
literally (`< 0x9C3F`, `< 0xC34F`, `< 0xEA5F`) — off-by-one on all three
large thresholds. Source constants: **40000, 50000, 60000**.

**Lesson:** when the target compares via `ori IMM; sltu reg,IMM_reg,x`,
the source constant is `IMM + 1`.

After fixing all three in one rewrite: 9/49 → and the entire comparison
tail was already structurally aligned.

## Phase 2 — two codegen levers (the reusable part)

With semantics right, the remaining fight was the 8-instruction head.
Four hypotheses (v11–v14) were fuzzed side-by-side in full mode; comparing
them isolated two distinct mechanisms, which v15 then combined for 49/49.

### Lever A — statement-split sign-extension positions the combined shift

Target head:

```
0 sll a0,a0,16
1 lui a1,%hi(D_8006C838)
2 lui v0,%hi(D_80055988)
3 addiu v0,v0,%lo(D_80055988)
4 sra a0,a0,15        <- merged shift lands HERE, after the symbol setup
5 addu a0,a0,v0
6 lh  v1,0(a0)
7 addiu a1,a1,%lo(D_8006C838)   <- scheduler moved this into the lh delay slot
```

combine.c merges `sra16` (sign-extension) + `sll1` (×2 scaling) into
`sra15` **at the position of the last merged insn** (the scaling shift).
For the merged shift to land at [4] — after both symbol address setups —
the sign-extension must be expanded in an **earlier statement** than the
array access, so its `sra16` can be consumed by the merge while `sll16`
stays behind at [0]:

```c
idx = (s16)arg0;                 /* sll16, sra16 expanded here ... */
base = (char *)&D_8006C838;      /* lui a1, addiu a1 */
val = D_80055988[idx];           /* ... sra16 consumed by merge with the ×2
                                    at the access site -> sra15 at [4]   */
```

Single-expression forms (`D_80055988[(s16)arg0]` with the base folded in)
expand the sign-extension adjacent to the access, so the merged shift lands
next to `sll16` — wrong order. Observed scheduler behavior on this R3000
function: it only filled the `lh`→chain load-delay slot with `addiu a1`
and otherwise **preserved expand order** — head-order matching here was an
expand-order (statement structure) problem, not a scheduler-priority one.

### Lever B — MIPS `LEGITIMIZE_ADDRESS` 0x8000-boundary split needs a bare REG

Target epilogue of the address computation:

```
addu v0,v0,a1        scaled + base
ori  v1,zero,0x8000  v1 = 0x99EC & ~0x7fff
addu v0,v0,v1
lhu  a0,0x19EC(v0)        0x99EC & 0x7fff
```

The vendored MIPS backend (`config/mips/mips.h`, `LEGITIMIZE_ADDRESS` —
verified in the 2.8.1-psyq tree; same era logic as 2.95.2) transforms
`memory(X + <large int>)` into `Z = X + (C & ~0x7fff); memory(Z + (C & 0x7fff))`
**only when the address reaching it is `plus(REG, CONST_INT)` with the
constant out of range**. Two shapes were tested:

| shape | address at legitimize | result |
|---|---|---|
| `*(u16*)(base + val*468 + 0x99EC)` (one expression) | `plus(plus(reg,reg), 0x99EC)` | macro doesn't fire (op0 is PLUS, not REG) → generic explow.c `force_operand` materializes **0x99EC whole**: `li v1,0x99EC; addu; lhu 0(v0)` (v11/v16) |
| `ptr = base + val*468;` then `*(u16*)(ptr + 0x99EC)` | `plus(reg, 0x99EC)` | macro fires → `ori 0x8000; addu; lhu 0x19EC` (v13/v15) ✓ |

**Lever:** when the target shows a large constant split as
`li C&~0x7fff; addu; mem [reg + C&0x7fff]`, the original source attached
that constant **only at the final dereference**, with the base+scaled sum
already materialized as its own pseudo (separate statement). Folding
everything into one address expression takes the generic path and
materializes the constant wholesale.

## Tooling bug found: finalize scope gate path mangling

`psx_finalize_function` failed on a phantom path `nclude/functions.h`
(note the missing `i`) as "outside the configured integration roots".

**Root cause:** `.pi/extensions/psx-decomp/autonomous/workspace.ts` — the
`git()` helper returns `result.stdout.trim()`. For
`git status --porcelain=v1` the first line is `" M include/functions.h"`;
the leading-trim strips its status-column space (`"M include/..."`), so the
parser's `line.slice(3)` eats one character of the path. The mangled
`nclude/...` then fails the `allowedRoots` (`src`/`include`/`configs`)
check. Same latent bug in `trackedDirtyFiles` (same `slice(3)` pattern).

**Fix:** `.trim()` → `.trimEnd()` in the `git()` helper (comment added).
Verified with a debug harness: paths parse cleanly afterwards.

**Aftermath / known limitation:** after the fix, the scope gate fails only
on the fix file itself — `.pi/` is outside `allowedRoots` and the session
baseline (`tools/session-baseline.ts`, captured once at extension
activation) predates the edit. The baseline re-snapshots at the next
session start, at which point finalization passes all four gates (exact
diff ✓, full build ✓, scope ✓, clean-source ✓). Confirmed independently:
`make check` reports the full payload byte-identical.

## Takeaways for the playbook

1. **Decode arithmetic before fuzzing shapes.** Three of the four lost
   hours went to fuzzing 10 variants against wrong semantics. Shift pairs,
   strength-reduction chains, and `ori+sltu` compare idioms each have an
   exact decimal reading — compute it first.
2. **`ori IMM; sltu r,r,x` ⇔ source constant `IMM+1`** (sltiu sign-extends;
   constants ≥ 0x8000 can't use it).
3. **Combined shift placement = statement structure.** A `sra` fused from
   sign-extension + scaling lands at the scaling site; an earlier
   sign-extension statement lets combine consume the `sra16`, leaving
   `sll16` at the top and the merged shift wherever the scaling happens.
4. **Large address constants split only at a bare-REG MEM address**
   (MIPS `LEGITIMIZE_ADDRESS`). Give the base+scaled sum its own statement
   and put the big offset on the final dereference.
5. **This R3000 scheduler mostly preserves expand order**, filling only
   load-delay slots — match head order via statement order, not by
   expecting the scheduler to hoist.
