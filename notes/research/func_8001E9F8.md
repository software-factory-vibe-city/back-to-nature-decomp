## RESOLVED — 59/59, byte-verified, make check OK (2026-07-31)

The conclusion above was close: the phantom did need an un-DCE-able live
range. The construct is a **file-scope global register variable**:

```c
register s32 hidden asm("$2");   /* file scope, before the function */
```

GCC semantics that make this the unique answer (all verified):

1. Stores to a global register variable are never deleted — the four
   `move $v0,$s0` re-installs (`hidden = saved;` before each call) survive
   even though $v0 is call-clobbered immediately after.
2. The register is reserved for allocation for the rest of the TU — the
   vertex-pool base lands in $v1/$a2 instead of $v0, matching the target,
   and no scratch web ever touches $v0.
3. Reads after a call (`return hidden;` / `if (hidden == 0)`) read the
   callee's return value directly — the calls are declared void and the
   whole file's results travel through the $v0 channel.
4. Declaration position matters: a mid-file declaration takes effect for
   functions compiled after it. In the original single source file it sat
   between func_8001E878 (still uses $v0 as scratch) and func_8001E9F8.
   In our per-function TU layout it simply heads func_8001E9F8.c.

Ruled out along the way (each compiled and word-diffed):
- block-scope pin + dead store only: capture dies at entry, 40-byte frame;
- `hidden = saved` with block-scope pin: deleted as no-op self-copy;
- asm-redefinition (`"=r"`) to break the copy chain: entry chain broken but
  re-installs still DCE'd;
- void-call + `return hidden` with block-scope pin: call's def of $v0
  satisfies the read, sets still dead (51 insns);
- empty-asm use (`:: "r"(hidden)`): moves survive but $v0 freed at the use
  point, base steals it (61 insns, register roles shifted).

## Provenance addendum: why $2, and what the callers reveal

Question raised after the match: $2 seems arbitrary. It is not — it has two
special roles that make it the plausible target of a deliberate binding:
the MIPS return-value register, and GCC's STATIC_CHAIN_REGNUM (verified in
the vendored mips.h), i.e. the register nested functions receive their
parent frame in.

**Nested-function hypothesis: tested and disproven.** If these were GNU
nested functions, every caller would load the static chain into $2 before
each call, and cross-file calls by symbol would be impossible (nested
functions have no linkage). The actual caller evidence
(build/asm/nonmatchings/func_8001EAE4/func_8001EAE4.s): func_8001EAE4 makes
4 calls to each function; before the func_8001E9F8 calls, $v0 holds
`polyFlags & D_8005E4FC` — the *skip test residue*, which is zero on every
path that reaches the call; before the func_8001E878 calls there is no $v0
setup at all. Callers treat both as plain functions.

**Conclusion**: the $2 manipulation is entirely callee-side. The original
file declared a $2-bound register variable and assigned/read it inside these
two functions only; its captured value at runtime is the caller's leftover
zero, and every read is dead in retail. Two period-plausible narratives fit
equally: (a) an instrumentation/debug channel whose consumers were
compiled out, (b) a "fast register global" placed on a call-clobbered
register (a classic mistake GCC's manual warns about) with manual
save/restore around calls. The bytes cannot distinguish intent further;
the construct class itself is pinned by the §9.1(b) impossibility argument
plus the reservation fingerprint ($v0 absent from all scratch webs in this
function, present in func_8001E878's).
