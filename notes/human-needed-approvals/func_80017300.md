## Where it stands

either an RLE row stream, an RLE two-channel column stream, or a raw byte row
stream into `D_8005EE28`, optionally ORs 0x8000 into every pixel after the
first, then `LoadImage` + `DrawSync` per scanline.

## The 7 remaining words — three coupled compiler-state ties

Each was measured from the dumps, not inferred from the emitted code.

1. **Preheader emission order** (3 branches, ~3 words). Target emits
   `[lui %hi(D_8005EE28), andi s6,a0,2, addu s7,t0,zero]`; the attempt emits
   `[andi, lui, move]`. The lui/copy pair is **gcse-PRE**-created (the
   D_8005EE28 hi pseudo: 3 sets, caller-saved to 0x38); the `andi` is
   **loop.c**-hoisted. `schedulerTrace --pass sched2` reports the block as
   already in that RTL order ("only candidate" / "tie broken by original
   position"), so the scheduler is not the actor — the two passes' insertion
   order is. All three insns **tie on priority**, so the order is decided
   purely by **LUID**: bottom-up, the target needs `high < and < move`; the
   attempt has `and < high < move`. The fix therefore has to land in the RTL
   order reaching sched2, not in the scheduler.

   That RTL order is `loop.c`'s movable-emission order, which follows the
   loop-body RTL order (`scan_loop` appends via `last_movable->next`;
   `move_movables` emits each with `emit_insn_before(..., loop_start)`). In
   the `.gcse` dump, block 9 (the row-loop top) reads
   `high->reg150 (insn 220), lo_sum->dst (221), and->flags2 (224),
   next_row (227), high->reg274 (insn 1032), jump`. Insn 1032 is a **gcse-PRE
   insertion placed at the END of the block** (`insert_insn_end_bb`), and it
   is the one `loop.c` hoists — which is exactly why it always lands after
   the `and`, and why **source statement order in the loop body is inert**
   (verified with `dst` before and after `flags2`).

   **The decisive observation** (`.loop` dump, i.e. after loop.c — do not
   re-derive this): loop.c hoists *three* insns into that preheader, in this
   order:

   ```
   (insn 1094)  reg116 = and(reg100, 2)                    <- flags2
   (insn 1095)  reg274 = high(D_8005EE28)                  <- gcse's pseudo
   (insn 1099)  reg150 = high(D_8005EE28)   [REG_EQUAL]    <- original insn 220
   ```

   cse2 then rewrites 1099 into `reg150 = reg274`, which is the emitted
   `addu s7,t0,zero`. So the movable list order is `[and(224), high(1032),
   high(220)]` — which is neither the loop-body RTL order (220 < 224 < 1032)
   nor its reverse, so `scan_loop`'s append order is not simply RTL order for
   this mix of original and gcse-inserted insns.

   The target's equivalent must be `[high(gcse), and, copy]`. That is what you
   get if gcse's insertion lands on the **loop-entry edge** (already in the
   preheader, so loop.c never hoists it and appends the `and` after it),
   instead of at the end of the loop-top block. Nothing at source level was
   found that moves gcse's insertion point: 18 declaration positions for
   `entry_data` (the only register in the `and` expression's gcse hash), a
   `u16 D_8005EE28[0x100]` declaration, and every statement permutation of
   `dst` / `flags2` / `next_row` all reproduce `[andi, lui, move]`.

   **gcse.c has now been read, and the compiler states the decision itself.**
   The `.gcse` dump carries PRE's own diagnostics:

   ```
   PRE: redundant insn 366 (expression 38) in bb 22, reaching reg is 274
   ... (also bb 23, 28, 42, 43, 52, 53)
   PRE/HOIST: end of bb 9,  insn 1032, copying expression 38 to reg 274
   PRE/HOIST: end of bb 27, insn 1041, copying expression 38 to reg 274
   PRE/HOIST: end of bb 46, insn 1056, copying expression 38 to reg 274
   ```

   Expression 38 is `high(D_8005EE28)`. bb 9/27/46 are the three row-loop-top
   blocks; bb 8 (start 974, end 213) is branch A's preheader. PRE deletes the
   flag-pass and LoadImage occurrences and inserts its own computation at the
   **end of the loop-top block** — necessarily after the `andi`. bb 9's own
   `high` (insn 220) is *not* in the redundant list, so it survives and loop.c
   hoists it in pass 2, becoming the emitted `addu s7,t0,zero`.

   The root cause is structural in 2.95: `compute_pre_data` calls
   `pre_lcm (n_basic_blocks, n_exprs, s_preds, s_succs, transp, antloc,
   pre_redundant, pre_optimal)` — **without the `comp` (available) bitmap**.
   Placement is decided from transparency and anticipatability alone, so the
   computation already present at the top of bb 9 is invisible to it, and the
   lazy (latest) placement is bb 9's end. For the target's order, PRE would
   have to insert at the end of bb 8 instead.

## Mechanisms that DID resolve (keep these)

- `flags2 = entry_data & 2` must be an **always-executed statement at the top
  of the row-loop body**. Computing it before the height guard leaves it in the
  wrong basic block; inlining it at the use site puts it past a `maybe_never`
  point in `scan_loop` and it is never hoisted at all (that variant loses 100+
  words to a count delta).
- **Split `header` from the flags variable.** Keeping the raw word in its own
  local is what holds the 0xFFFFFF constant live in `$v0` across the `rect.h`
  load, which forces that load into `$v1` and pins `sh v1,22(sp)` ahead of
  `andi v1,a0,3`. This single change fixed the entire loop-head cluster.
- **Declaration order is not inert here.** It sets pseudo numbers, which set the
  gcse expression-hash bucket order for `size + 3` versus `entry_idx + 1`, which
  decides which of the two owns caller-save slot 0x2C versus 0x30.
  `entry_idx` must be declared at least three slots after `size`
  (`hash(REGNO(size)+3) < hash(REGNO(idx)+1)`); adjacent declarations collide in
  the same bucket and keep the wrong order. Worth 8 words.
- A **fresh `bytes` local** for the rounded byte count, rather than assigning
  back into `size`, restores the target's single-`$v0` tail chain.
- `rect.h = 1;` before `row = 0;` (natural `for`-init order).
